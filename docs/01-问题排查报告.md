# 问题排查报告：图生图提示「服务异常」

## 一、现象

在图形界面中使用「图片生图」模式，选择参考图并确认「参考图片与提示词将发送给 Agnes 云服务」后，任务失败并弹出「服务异常」类提示。文字生图模式下未观察到该现象。

## 二、结论速览

| 结论 | 说明 |
| --- | --- |
| 工具是否必须联网调用 Agnes API | **是**。生图请求发往 Agnes 云接口，必须使用 API Key |
| 图生图协议本身是否有问题 | **否**。实测多组参考图均返回 200 |
| 「服务异常」的直接来源 | 原代码捕获 HTTP 错误时**丢弃了服务端返回的 `error.message`**，5xx 统一显示「服务暂时异常，请稍后手动重试」 |
| 能否稳定复现 5xx | **未能复现**。说明该故障与账号额度、限流或服务端偶发状态相关，而非调用方式错误 |
| 已做修复 | 错误信息附带服务端原文；新增个人 Key 配置与 Key 校验 |

## 三、排查过程

排查按三层展开：**协议层 → 工具层 → 账号层**。

### 3.1 协议层：接口是否接受图生图请求

直接构造 HTTP 请求，绕过工具，分别测试三种参数放置方式：

| 用例 | 参考图参数位置 | 结果 |
| --- | --- | --- |
| A | `extra_body.image`（列表） | **200**，返回 `i2i` 通道结果 |
| B | 顶层 `image`（列表） | **403** `PermissionDeniedError: Model is blocked` |
| C | 顶层 `image`（字符串） | **403** `PermissionDeniedError: Model is blocked` |

结论：工具现有的 `extra_body.image` 写法是**正确**的。把 `image` 放到顶层会被网关当作对话请求处理，从而触发「模型被阻断」。

### 3.2 协议层：参考图体积是否触发失败

| 参考图 | 原始体积 | base64 后 | 结果 | 耗时 |
| --- | --- | --- | --- | --- |
| 64×64 PNG | 极小 | 极小 | 200 | — |
| 1024×1024 JPEG | 0.76 MB | 1.01 MB | 200 | 约 20 s |
| 2048×1536 JPEG | 2.69 MB | 3.58 MB | 200 | 约 30 s |
| 3000×2000 JPEG | 6.71 MB | 8.94 MB | 200 | 约 35 s |

结论：在工具允许的 10 MB 上限内，参考图体积**不是**失败原因。

### 3.3 工具层：完整链路是否可跑通

使用命令行执行图片生图，走完整流程（校验 → 提交 → 下载 → 落盘）：

```
<JOB_ID>
第 1/1 张：已提交，等待生成（无真实百分比）
第 1/1 张：下载并校验结果
<输出目录>/<JOB_ID>_01.png
任务 <JOB_ID>：success
```

结论：工具自身的图生图链路**正常**。

### 3.4 账号层：Key 的有效性与权限

| 用例 | 结果 |
| --- | --- |
| 无效 Key 调用生图接口 | 401 `Invalid token` |
| 有效 Key 调用生图接口（参数非法） | 400 `size has invalid value "__invalid__"; must be one of: 1K, 2K, 3K, 4K, or WIDTHxHEIGHT` |

结论：接口**先校验鉴权、再校验参数**。这一特性被用作无成本的 Key 校验探针（见 [02-API-Key-配置说明.md](02-API-Key-配置说明.md)）。

## 四、根因分析

原代码的错误映射函数只依据 HTTP 状态码生成提示：

```python
message = messages.get(
    code,
    "服务暂时异常，请稍后手动重试。" if code >= 500 else "服务拒绝请求，请检查配置。"
)
```

服务端返回的 `error.message`（例如 `Invalid token`、`Model is blocked`、额度或限流相关提示）**被整体丢弃**。因此当账号侧出现额度不足、限流或服务端偶发错误时，用户只能看到一句无法定位的「服务异常」，无法判断是 Key 失效、权限不足还是配额耗尽。

同时，原工具**没有提供填写个人 Key 的入口**，只能回退使用系统模型配置中的对话模型 Key。该 Key 的额度与权限不由使用者掌控，一旦被限流或回收，就会表现为「服务异常」而没有任何可操作线索。

## 五、已实施的修复

| 编号 | 修复项 | 效果 |
| --- | --- | --- |
| 1 | 新增 `_server_message()`，解析 HTTPError 响应体中的 `error.message` | 错误提示附带上游真实原因，例如 `HTTP 403：当前 Key 无权限使用该模型。 服务端返回：PermissionDeniedError: Model is blocked` |
| 2 | 新增个人 API Key 配置（`api_config.json`） | 使用者用自己的 Key，额度与权限可控 |
| 3 | 新增 `test_api_key()` 无成本校验 | 保存前后可一键确认 Key 是否有效 |
| 4 | 界面新增 API 设置栏与状态显示 | 随时可见当前生效的 Key 来源（掩码） |

## 六、仍未覆盖的场景

以下内容本次**未能复现**，因此未做代码层面的针对性处理，仅提升了可观测性：

- 服务端 5xx 偶发错误；
- 账号额度耗尽或限流（429）时的具体表现；
- 特定图片编码（如带 Alpha 通道的 PNG、CMYK JPEG）在下游处理中的行为。

若再次出现失败，现在可以直接从弹窗中的「服务端返回：…」读取真实原因，据此判断是换 Key、降规格还是稍后重试。
